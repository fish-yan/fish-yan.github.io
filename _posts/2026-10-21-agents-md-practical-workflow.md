如果 Codex 经常用错测试命令，或者你只要求分析，它却直接修改了文件，可以把项目约定写进 `AGENTS.md`。这篇文章给出一个最小模板，并说明如何检查文件是否被读取、规则是否被执行。

## 1. 从反复出现的具体问题开始

把要求写成能执行的动作：

| 含糊的要求 | 可检查的写法 |
|---|---|
| 确保质量 | 修改分页逻辑后执行 `python3 -m unittest discover -s tests -v`，报告结果 |
| 不要乱改 | 用户只要求分析时，不修改文件 |
| 注意兼容性 | 保留既有函数签名；行为变化必须在说明中列出 |

命令必须与当前仓库相符；只对某次任务适用的要求，留在该次对话中即可。

## 2. 先弄清文件如何被发现

根据 [Codex 的 AGENTS.md 官方文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)，指导文件按全局和项目层级组合：全局通常从 Codex home 读取；项目层级从仓库根走到工作目录。每层优先查找 `AGENTS.override.md`，再查找 `AGENTS.md`，更近的规则覆盖更早的对应约定。

这意味着下面的目录结构需要与实际启动位置一起理解：

```text
repo/
├── AGENTS.md
└── services/
    └── api/
        ├── AGENTS.md
        └── ...
```

如果希望启动时纳入 `api` 层的规则，就从对应工作目录开始。不要仅凭“这次要修改 api 文件”，便断言初始化时已经自动读取了那一层；需要时明确要求读取该文件，并核对当前工具的行为。

文件也不宜无限增长。官方 [Advanced Configuration](https://learn.chatgpt.com/docs/config-file/config-advanced) 提供了项目文档字节上限与备用文件名配置；[指导文件说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 给出的默认 `project_doc_max_bytes` 为 32 KiB。达到上限时，后续内容可能无法完整进入指导上下文，关键约定应保持简短。

## 3. 一份最小模板

下面用一个 Python 分页函数的教学目录示范。

```markdown
# 协作约定

## 项目与验证
- 当前目录是分页函数的教学示例，不代表生产项目。
- 从此目录运行：python3 -m unittest discover -s tests -v。

## 修改边界
- 实现位于 pagination.py，测试位于 tests/。
- 用户只要求分析时不修改代码。
- 不新增第三方依赖，不自动提交或推送。

## 完成条件
- 覆盖空输入、整页、尾页不足一页及非法范围。
- 最终说明修改目的、执行的检查及尚未验证的内容。
- 命令失败或未执行时如实说明。
```

这里限定不新增依赖，是因为示例只需要整数计算和标准库测试；换成已有项目，应沿用项目实际的依赖管理要求。官方 [Best practices](https://learn.chatgpt.com/docs/learn/best-practices) 也建议保持指导简短、准确，并写清构建、测试和完成条件。

## 4. 检查一次任务是否按规则完成

可以给协作者这样一个任务：

> 实现 page_count(total, page_size)。参数约定为整数：total 不得为负，page_size 必须大于零。空数据返回零页，尾页不足一页仍计入一页。不要新增依赖或提交 Git。先确认相关规则，完成后给出验证结果。

验收时先检查这些输入，不需要从实现反推正确答案：

| 输入 | 预期 |
|---|---|
| `0, 10` | `0` |
| `20, 10` | `2` |
| `21, 10` | `3` |
| `-1, 10` | 抛出 `ValueError` |
| `10, 0` 或 `10, -1` | 抛出 `ValueError` |

从示例目录执行测试：

```sh
python3 -m unittest discover -s tests -v
```

配套函数已在 Python 3.13.1 下测试，5 个测试方法通过，非法分页大小包含两个子用例。**这些测试检查的是分页函数，不是 AI 是否遵守规则。** 要验收后者，还需检查实际会话的执行记录：是否在正确目录运行测试、是否修改了范围外的文件、是否发生了未经要求的提交。

## 5. 区分读取、执行和验证

想检查指导文件是否进入上下文，可以在新会话中先提出一个只读请求：

> 列出本次任务使用的指导文件路径，指出测试命令和修改边界。只读取，不修改，不执行发布操作。

若使用 CLI，可以显式指定目录；先核对自己版本的选项：

```sh
codex --version
codex --help
codex --cd services/api --sandbox read-only \
  '列出当前适用的指导文件、测试命令与修改边界，只读取。'
```
助手能复述规则，不等于已经执行。检查任务结果时，直接查看测试命令及退出状态、测试输出和文件 diff；只有计划、没有执行输出时，不能记为验证通过。

当测试命令不存在时，正确结果应是报告入口失效并提出修正，而不是把计划执行写成已经通过。

## 6. 文本约定还需要工具与工程机制配合

`AGENTS.md` 中写下“不要访问某个目录”，不会自动改变操作系统权限。Codex 的 [Sandbox 文档](https://learn.chatgpt.com/docs/sandboxing) 描述了沙箱限制与审批机制，它们需要在工具层配置。

格式要求可以由格式化工具或 CI 检查，类型要求由编译器检查，发布权限由发布流程控制。`AGENTS.md` 写明入口和操作约定，不替代这些检查。

同理，不要把令牌或密码写进指导文件。需要秘密信息的任务，应通过合适的凭据机制接入；仓库里的规则只说明如何使用已有能力，不保存凭据本身。

## 7. 把规则当成需要维护的工程文件

测试目录、包管理器或构建入口变化时，同步更新对应命令。同类问题再次出现时，先检查规则是否被读取、命令是否仍有效，再决定补充哪条约定；不要在旧要求后面不断追加互相矛盾的新要求。
